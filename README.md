# 글쓴이 안내서

이 저장소는 `content/` 아래에 글을 기록하고 정적 사이트를 만드는 작은 사이트입니다. 글쓴이는
파일을 고친 뒤 실제 명령인 `npm run build`를 실행하고, 방문자는 만들어진 `docs/`의 페이지를
읽습니다.
아래 예시는 파일 이름과 경로까지 포함한 완전한 파일이므로 그대로 복사해 시작할 수 있습니다.

## 새 글 쓰기

새 글은 `content/posts/<id>.md`로 저장합니다. `<id>`는 글을 쓴 시각(UTC)을 `YYYYMMDD-HHMMSS` 모양으로 쓴
이름입니다. 예를 들어 2026년 9월 23일 14시 00분 00초(UTC)에 쓴 글은 `20260923-140000.md`이고, 헤더의 `written`도 같은
시각이어야 합니다. 이름이 이 모양이 아니거나 `written`과 다르면 빌드 오류가 납니다. 제목은 이름에 넣지 않습니다.
헤더와 본문 사이에는 빈 줄을 하나 둡니다.

헤더에는 다음 세 필드를 씁니다. 태그는 헤더에 쓰지 않고 아래 "태그 달기"처럼 태그 표에 답니다.

- `written`: UTC 시각을 `YYYY-MM-DDTHH:MM:SSZ` 모양으로 씁니다. 예를 들어
  `2026-09-23T14:00:00Z`입니다.
- `type`: `short`, `medium`, `long` 중 하나입니다. `short` 글에는 `title`을 쓰지
  않고, 제목이 필요한 중간 글과 긴 글에는 `title`을 씁니다.
- `title`: `medium` 또는 `long` 글의 제목입니다. 따옴표 없이 한 줄로 씁니다.

다음은 제목을 갖춘 중간 글의 완전한 예입니다.

```post content/posts/20260923-140000.md
written: 2026-09-23T14:00:00Z
type: medium
title: 첫 번째 기록

여기서 글을 시작합니다. 이 글에는 다른 글로 이어지는 출발점이 있습니다.

### 작은 제목

**굵은 글씨**, *기울임*, `코드`를 쓸 수 있습니다.
```

본문은 일반 문단과 `#`, `##`, `###` 제목, `- `로 시작하는 목록, `> `로 시작하는
인용문, **굵게**, *기울임*, `인라인 코드`를 지원합니다. 빈 줄로 문단을 나누고, 문단 안에서 줄을 바꾸면 화면에서도 그 자리에서 줄이 바뀝니다.
마크다운 문법의 기호를 필요한 자리에 그대로 씁니다.
바깥 링크는 `[글자](주소)`로 쓰며, 주소는 `http://`나 `https://`로 시작해야 합니다.

이미지는 먼저 실제 파일을 `content/images/사진.jpg`처럼 넣은 다음 본문에
`![사진 설명](images/사진.jpg)`라고 씁니다. 경로는 반드시 `images/`로 시작해야 하며,
대체 글자는 방문자에게 이미지 설명으로 보입니다. 이미지가 너무 크면 설명 뒤에 `|`와 너비를 붙여
`![사진 설명|160](images/사진.jpg)`처럼 씁니다. 숫자는 화면에 보이는 너비(CSS 픽셀)이고, 높이는 비율대로 따라갑니다.
원본 파일은 바뀌지 않습니다. 파일이 없거나 다른 경로를 쓰면 빌드
오류가 납니다.
본문의 그림을 누르면 원본이 화면 위에 크게 보입니다.

제목이 없는 짧은 글은 아래처럼 쓸 수 있습니다.

```post content/posts/20260923-140100.md
written: 2026-09-23T14:01:00Z
type: short

이 글은 링크가 가리킬 대상입니다.
```

## 기록 표에 대해

링크, 패치, 공유, 태그는 글 파일이 아니라 기록 표에 남깁니다. 기록 표는 `content/` 바로 아래의 `.jsonl` 파일이고, 한 줄이
기록 하나입니다. 줄은 덧붙이기만 하고 지난 줄은 고치지 않습니다. 링크를 지우거나 태그를 떼는 것도 줄을 하나 더해서 합니다.
그래서 언제 무엇을 왜 했는지가 표에 그대로 남습니다. 지금 살아 있는 링크나 지금 달린 태그는 빌드가 표를 읽어 계산합니다.
어느 줄이 잘못되면 빌드 오류가 `content/links.jsonl:3`처럼 파일과 줄 번호를 알려줍니다.

## 링크 걸기

링크는 `content/links.jsonl`에 줄로 적습니다. 링크를 거는 줄에는 `link`, `from`, `to`, `anchor`, `action`, `at`, `why`를
씁니다. `link`는 링크의 이름(영문 소문자, 숫자, 하이픈), `from`과 `to`는 글의 id, `action`은 `created`, `at`은 UTC 시각,
`why`는 링크를 건 이유입니다. `anchor`는 출발 글 본문에 실제로 한 번만 나오는 문장 일부여야 합니다. 빌더는 그 글자에 `[n]`
표시를 붙여 도착 글로 연결합니다.

사유를 바꾸려면 같은 `link`로 `action`이 `reason-changed`인 줄을, 링크를 지우려면 `removed`인 줄을 더합니다. 이런 줄에는
`link`, `action`, `at`, `why`만 씁니다. 줄의 시각은 앞선 줄보다 이르면 안 되고, 한 링크의 첫 줄은 `created`여야 합니다.
마지막 줄이 `removed`이면 방문자에게 링크가 나타나지 않지만 기록은 남습니다.

다음은 링크를 걸고 사유를 한 번 바꾼 두 줄입니다.

```link content/links.jsonl
{"link": "first-link", "from": "20260923-140000", "to": "20260923-140100", "anchor": "다른 글", "action": "created", "at": "2026-09-23T14:02:00Z", "why": "관련된 글을 연결함"}
{"link": "first-link", "action": "reason-changed", "at": "2026-09-23T14:03:00Z", "why": "독자가 다음 글을 이어서 읽도록 안내함"}
```

## 패치 붙이기

패치는 원문을 고치지 않고 방문자에게 보이는 결과를 바꾸는 기록입니다. `content/patches.jsonl`에 한 줄로
`id`, `post`, `at`, `why`, `op`, `anchor`를 씁니다. `id`는 패치의 이름(영문 소문자, 숫자, 하이픈)으로 표 안에서 한 번만
쓰고, `post`는 바꿀 글의 id, `at`은 UTC 시각, `why`는 변경 이유, `anchor`는 현재 본문에 정확히 한 번 있는 글자입니다.

`op`에는 네 가지가 있습니다. `replace`는 `anchor`를 `text`로 바꾸고,
`insert-before`는 anchor 앞에 `text`를 넣으며, `insert-after`는 뒤에 넣습니다.
`delete`는 anchor를 지웁니다. `delete`에는 `text` 필드를 쓰지 않고, 나머지 세 연산에는
`text`를 반드시 씁니다. 패치는 `at`이 이른 것부터, 같은 시간이면 `id`의 글자순으로
적용되므로 뒤의 패치가 앞 패치가 만든 글자를 anchor로 삼을 수 있습니다.

다음은 `20260923-140000` 글의 `출발점`을 `안내점`으로 바꾸는 패치 한 줄입니다.

```patch content/patches.jsonl
{"id": "first-wording", "post": "20260923-140000", "at": "2026-09-23T14:04:00Z", "why": "표현을 더 분명하게 고침", "op": "replace", "anchor": "출발점", "text": "안내점"}
```

## 공유 기록 남기기

글을 X, 스레드, 링크드인 같은 곳에 공유했다면 `content/shares.jsonl`에 줄을 하나 더합니다. 그러면 피드 항목과 글 페이지
하단에 각 곳의 공식 로고 배지가 붙고, 배지를 누르면 공유한 글로 갑니다. 글 파일은 고치지 않습니다.

줄의 필드는 `post`, `where`, `url`, `at`입니다. `post`는 공유한 글의 id, `where`는 공유한 곳, `url`은 공유한 글의
주소(`https://`로 시작), `at`은 공유한 시각(UTC)입니다. `where`에는 지금 `x`, `threads`, `linkedin`, `substack`, `bluesky`를 쓸 수 있습니다.
다른 곳을 쓰고 싶으면 사이트에 그곳의 이름과 공식 로고 파일을 먼저 더해야 합니다. 한 글을 여러 곳에 공유했다면 곳마다 한 줄씩
더하고, 배지는 공유한 순서대로 붙습니다.

```share content/shares.jsonl
{"post": "20260923-140000", "where": "x", "url": "https://x.com/someone/status/1", "at": "2026-09-23T15:00:00Z"}
```

## 태그 달기

태그는 `content/tags.jsonl`에 줄로 답니다. 줄의 필드는 `post`, `tag`, `action`, `at`, `why`입니다. `post`는 글의 id,
`tag`는 태그 이름, `action`은 `added`(달기) 또는 `removed`(떼기), `at`은 UTC 시각, `why`는 그렇게 한 이유입니다. 태그
이름은 40자 이하이고 앞뒤에 공백이 없으며 `/`나 `\`를 쓰지 않습니다. 한 글·태그 짝의 첫 줄은 `added`이고, 그 뒤로는
`added`와 `removed`가 번갈아 옵니다. 떼었던 태그를 다시 달 수도 있습니다.

태그 목록은 따로 관리하지 않습니다. 빌드가 표를 읽어 글마다 지금 달린 태그를 계산하고, 피드 옆에 태그 클라우드를,
태그마다 그 태그가 달린 글을 모은 페이지(`/tags/<태그>/`)를 만듭니다. 글 페이지의 태그는 그 페이지로 가는 링크입니다.

```tag content/tags.jsonl
{"post": "20260923-140000", "tag": "기록", "action": "added", "at": "2026-09-23T14:05:00Z", "why": "첫 기록이라서"}
{"post": "20260923-140100", "tag": "기록", "action": "added", "at": "2026-09-23T14:06:00Z", "why": "연결 대상 글도 기록으로 모음"}
```

## 소개 페이지 쓰기

소개 페이지는 사이트에 하나만 있는 글로, `content/about.md`에 씁니다. 이 파일은 반드시 있어야 하며, 없으면
빌드 오류가 납니다. 글과 달리 헤더가 없고 파일 전체가
본문입니다. 본문 문법은 글과 같으며, 바깥 링크 `[글자](주소)`를 쓸 수 있습니다. 주소는
`http://`나 `https://`로 시작해야 하고, 그렇지 않으면 빌드 오류가 납니다. 이미지는 글과 같이 `content/images/`에
넣고 `![설명](images/파일)`로 씁니다.

빌드는 이 파일로 `docs/about/index.html`을 만들고, 방문자는 사이트 주소 뒤의 `/about/`에서 봅니다. 모든 페이지
위쪽 메뉴에 `피드`와 `소개` 링크가 늘 있습니다. 소개 페이지는 글 페이지와 같은 모양으로 보입니다. 소개 글은
글 목록이나 피드에 나오지 않고, 링크나 패치의 대상도 아닙니다. 고칠 때는 이 파일을 직접 고칩니다.

```about content/about.md
![나](images/avatar.png)

안녕하세요. 생각나는 것을 적어 두는 곳입니다.

## 하는 일

LLM 시대의 개발 도구를 만듭니다. [저장소 보기](https://github.com/example)
```

## 사이트 만들기 — 빌드

처음 한 번은 저장소 루트에서 필요한 패키지를 설치합니다(Node 22 이상).

```sh
npm install
```

그 뒤로는 저장소 루트에서 다음 명령을 실행합니다.

```sh
npm run build
```

실행 명령 `npm run build`가 `content/`의 글, 링크, 패치를 읽어 방문자가 볼 정적 파일을
`docs/`에 새로 만듭니다. 만든 뒤에는
`docs/index.html`에서 목록을, `docs/p/<id>/index.html`에서
글 페이지를 확인합니다. 방문자에게 주소는 파일 이름 없이 보입니다: 첫 화면은 `/`, 글은 `/p/<id>/`, 소개는
`/about/`입니다. `docs/`는 호스트가 제공하는 결과 디렉터리이므로 생성된 HTML을
직접 고치지 말고 원본인 `content/`나 이 안내서의 규칙에 맞는 입력 파일을 고칩니다.

빌드가 실패하면 명령의 표준 오류인 `stderr`를 먼저 봅니다. 오류는 파일 경로를 담은 한 줄로
나오므로 그 줄의 `content/...` 경로에 있는 파일을 열어 형식, 날짜, id, anchor,
이미지 파일의 존재를 확인합니다. 예를 들어 링크 anchor가 본문에 없거나 두 번 나오면
링크 파일 경로가 표시되고, 패치의 anchor가 현재 글에 없거나 여러 번 나오면 패치 파일
경로가 표시됩니다. 고친 뒤 저장소 루트에서 `npm run build`를 다시 실행하면 됩니다.

## 방문자에게 보이는 모습

방문자가 처음 보는 `docs/index.html`에는 모든 글이 유형별로 나뉘지 않고 작성 시각의 최신순으로
나옵니다. 글마다 테두리가 있는 상자 하나입니다. 짧은 글은 제목 줄 없이 적용된 본문 전체를 보여주고,
중간 글과 긴 글은 굵은 제목을 보여줍니다. 상자 하단에는 작성 시각(독자 현지 시각)과, 공유한 곳이 있으면
그 배지가 붙습니다. 유형 이름(짧은 글/중간 글/긴 글)은 화면에 나오지 않습니다. 상자 어디를 누르든 그 글의
페이지로 가고, 배지만은 공유한 글로 갑니다. 글 페이지에는 그 글의 주석, 이 글을 가리키는 글, 패치 이력,
공유 배지가 모여 있습니다. 넓은 화면에서는 피드 오른쪽에, 모바일에서는 피드 아래에 태그 클라우드가 있어 태그를 누르면
그 태그가 달린 글만 모은 페이지로 갑니다. 글이 많이 달린 태그일수록 크게 보입니다.

제목이 없는 중간 글이나 긴 글은 제목 대신 적용된 본문의 첫 문단을 HTML로 만든 뒤 화면에
보이는 글자 중 앞 80자를 보여줍니다. 80자를 넘으면 `…`을 붙입니다. 마크다운 서식 기호와
HTML 태그는 글자 수에서 빼고 유니코드 문자 단위로 세며, 첫 문단이 이미지만으로 되어 있으면
이미지의 `alt` 설명을 사용합니다. 피드에 보이는 본문도 패치가 적용된 본문입니다.

패치가 하나 이상 있는 글 페이지에는
기본으로 꺼진 `패치 보기` 토글 버튼이 있습니다. 버튼을 켜면 패치가 바꾸거나 넣은 영역에
테두리(아웃라인)가 표시되고, 지운 자리에도 작은 표시가 남습니다. 표시된 영역에 마우스를
올리면 그 자리에 적용된 패치의 이력이 각 패치의 시각(독자 현지 시각), 사유, 종류, 이전
글자와 함께 보입니다. 버튼을 끄면 표시와 이력은 사라지고 패치가 적용된 본문만 보입니다.

한 패치의 영역은 그 패치가 넣은 글자입니다. `replace`와 `insert-before`, `insert-after`는
`text` 전체가 영역이고, `delete`는 지운 자리의 표시 하나입니다. 삭제 표시는 패치 보기를
끌 때는 자리를 차지하지 않습니다. 이후 패치가 그 영역의 일부를 다시 바꾸면 적용된 본문의
각 글자는 마지막으로 만든 패치의 영역에 속하고, 앞선 패치의 영역은 남은 글자만큼 줄어듭니다.
한 영역의 이력에는 그 영역의 글자를 만들거나 바꾼 패치가 시각 순으로 나오며, `replace`와
`delete`의 이전 글자는 anchor의 글자, `insert-*`의 이전 글자는 없음(“새로 넣음”)입니다.
